# The app stack for ValueIt

Research for ticket #8, "The leanest app stack for AI coding agents on Vercel".
Researched on 2026-11-27. Versions and limits are what the vendors' own docs and the public npm registry showed that day. This field moves monthly, so re-check a number before relying on it.

Three kinds of statement appear below and they are kept apart:

- **Fact**: stated by the vendor that owns the thing, with a link.
- **Measured**: a dated test by someone, with a link and its limits.
- **Opinion**: a judgement made here. It is labelled.

---

## 1. The answer

**Build ValueIt as one Next.js app, written in TypeScript, deployed on Vercel. Do not add a separate backend.**

### The recommended stack

| Piece | Choice | Why, in plain words |
| --- | --- | --- |
| Framework | **Next.js 16.4**, App Router, with "Cache Components" on (the default for a new app) | Vercel makes it, so the framework and the hosting are one vendor's problem. It can hand a Lesson page to the browser as a ready-made file and still stream a Chatbot answer. It ships its own up-to-date instructions for coding agents. |
| Language | **TypeScript**, strict mode, for everything | One language for the screen, the server and the database. One set of tools, and less for an agent to read. |
| Where code runs | **Vercel Functions on Node.js** (Vercel's default). Never the "edge" runtime | Edge is deprecated. Node is the default and has the long time limits. |
| Package manager | **pnpm** | Vercel supports it. By default it refuses to run install scripts from dependencies and waits a day before accepting a brand-new release, which protects against poisoned packages. |
| Reading and writing the database | **Drizzle** over a pooled Postgres connection to Neon. Changes to the tables are generated by Drizzle's tool and saved in the repo | The tables are described once, in TypeScript, and every query is checked against that description. This is the exact setup Neon documents for Vercel. |
| Styling and UI kit | **Tailwind CSS 4** with **shadcn/ui** | Tailwind is the Next.js default. shadcn copies the source of each button, slider and dialog into the repo, so an agent can read and change it. It has its own tooling for agents. |
| Charts | **Recharts 3**, through shadcn's chart component | The most used React chart library. It draws accessible charts and is plenty for teaching charts with tens of points. |
| Checking data | **Zod** | One way to check data wherever it enters: forms, the AI's output, settings. |
| Code checks | **Biome** for style and common mistakes, plus the TypeScript checker | One fast tool instead of two. (Opinion, see 2.8.) |
| Tests | **Vitest** for the calculator and the Widgets. **Playwright** for walking the Lesson in a real browser | These are the two tools the Next.js docs document. |
| CI | **GitHub Actions** runs the checks. **Vercel** builds a preview for every change and the live site on merge | Free for a public repo. Vercel's own CI product cannot run on public repos yet. |
| Long jobs | **Vercel Workflows**, used only when a job cannot fit inside one request | Same app, same language, same vendor. |
| Guidance for agents | A short `AGENTS.md` and one command, `pnpm check`, that says pass or fail | The measured gains come from a short pointer to the right docs and a check the agent can run by itself. |

### What it means for ValueIt

- **One thing to build, one thing to deploy.** Lesson pages, Widgets, the Chatbot and the admin page live in one codebase. A change is one pull request with one preview link.
- **A Lesson page can feel instant.** Because a Lesson's path is fixed and the same for every Student, the page can be prepared ahead of time and served as a file. The next step can be fetched before the Student clicks. Only the Chatbot and anything personal is worked out on demand.
- **Widgets should calculate in the Student's browser.** Moving a slider must not wait on a server. The same calculator code is tested against the spreadsheet's numbers.
- **The Chatbot streams.** Its words appear as they are produced. A single answer has a hard time limit: 5 minutes by default and about 13 minutes at most on the Pro plan. A 30-minute limit exists in beta.
- **Next.js is not the lightest choice for the browser.** In one independent test it sent more code to the browser than every other framework tested (2.2). It is recommended anyway because the pre-built page with a streamed Chatbot, the single vendor and the agent tooling matter more here. That trade is an opinion.

### A separate FastAPI backend: no

It does not earn its place. Every fixed piece has a first-class TypeScript path: OpenAI's SDK, A2UI (it has a Node agent SDK and a React renderer), Neon and Vercel. On Vercel a FastAPI app runs as one Vercel Function with the same time limits and the same streaming as the Next.js app, so it adds no ability. It would add a second language, a second set of tools and tests, a Vercel feature that is still in beta, and a seam between the two halves where types are lost.

**What would change this answer:**

1. A library that exists only in Python turns out to be needed *while a Student waits*. The likeliest candidate is the spreadsheet logic: if it cannot be rebuilt in TypeScript and match the original numbers.
2. A job needs a process that stays running all the time, or a GPU.
3. A second client, such as a phone app, needs its own public API.

If Python is needed only for a job done ahead of time, such as cutting up the material, that is a script or a single job step. It is still not a backend.

### Is the earlier base still right?

Yes. One Next.js app with Drizzle and Postgres is still the right base. Four things have changed and a fresh build should follow them:

1. **Caching is now something you ask for.** Nothing is cached unless the code says so, and the build fails if a page would be slow to appear and the code has not dealt with it.
2. **Reads and writes moved.** Pages read data directly on the server. Changes go through small server functions. A hand-written API endpoint is needed only for the streaming Chatbot.
3. **The database connection changed.** Neon now recommends an ordinary pooled connection on Vercel, not its special serverless driver.
4. **The framework now talks to agents.** It bundles its own version-matched docs and writes the pointer to them into `AGENTS.md`.

### What the owner has to understand, and nothing more

1. **There is one app.** Everything a Student or the owner sees comes from one codebase on Vercel.
2. **Three vendors run it.** Vercel runs the app. Neon keeps the data. OpenAI is the model. GitHub holds the code and runs the checks. (Sign-in is ticket #5.)
3. **Lesson pages are made ahead of time.** The Chatbot is made on demand. That split is what keeps a Lesson fast.
4. **Widgets work in the browser.** No waiting on a server to move a slider.
5. **Every change must pass the same automatic check** and gets its own preview link before it goes live.
6. **Keys live in Vercel**, not on a laptop, if long jobs run on Vercel too.
7. **Security updates to Next.js are not optional.** There were security fixes in October and November 2026, some of them critical. An agent can apply them with one command.

The defaults of a new app today are TypeScript, ESLint, Tailwind CSS, App Router, Cache Components, `AGENTS.md`, and no React Compiler ([create-next-app](https://nextjs.org/docs/app/api-reference/cli/create-next-app)).

How reads and writes are meant to work: keep sign-in checks and database code in one server-only module, keep server functions thin, and re-check the Student's rights inside every server function, because each one can be called directly ([Next.js: data security](https://nextjs.org/docs/app/guides/data-security)).

**How Next.js does with agents and in the browser.**

- Measured by the vendor: on Vercel's own Next.js tasks, last run 2026-10-30, the five strongest current models pass 100% with or without the `AGENTS.md` pointer. Cheaper models gain from it, for example 82% to 100% and 86% to 96%. A task counts as passed if any of four attempts passes. ([Next.js agent evals](https://nextjs.org/evals))
- Measured independently: one developer had an agent build the same small app five times in each of twelve frameworks ([Nolan Lawson, 2026-10-28](https://nolanlawson.com/2026/10/28/the-ai-cost-of-javascript-frameworks/)). Next.js 16.4.3 was mid-pack to build: $3.14 a build against a range of $2.67 to $4.97, and 10.9 minutes against 8.2 to 17.2. In the browser it shipped the most JavaScript of the twelve (142 KiB) and had the slowest largest-paint time (about 2.1 s). Limits: one small app, one model, five runs, and the author notes results are noisy.

Opinion: the other React-based choices in that test were only about 25 KiB lighter, and React is needed anyway for the Widgets and for A2UI's React renderer. The pre-built shell with a streamed Chatbot, the single vendor and the first-party agent tooling outweigh that. Astro would be lighter for plain Lesson text but would need more custom work to keep a Chatbot alive beside the Lesson from step to step.

### 2.3 Vercel limits today

All from [Vercel: Functions limits](https://vercel.com/docs/functions/limitations), [duration](https://vercel.com/docs/functions/configuring-functions/duration) and [Fluid compute](https://vercel.com/docs/fluid-compute).

| Limit | Value on Pro |
| --- | --- |
| Time one request may run | 300 s by default. 800 s maximum, generally available. 1800 s "extended maximum" in beta, set per function. |
| Does streaming count toward that? | Yes. The limit covers "sending the response, including streamed responses". |
| Memory and CPU | 2 GB and 1 vCPU by default, up to 4 GB and 2 vCPU. |
| Request and response size | 4.5 MB each. Streamed responses are exempt. |
| Billing | Active CPU time plus provisioned memory. Waiting on a model or a database does not count as CPU time. |
| Region | One region by default, `iad1`. |
| Fluid compute | On by default for new projects since 2025-04-23. One warm instance serves many requests. |
| Node.js versions | 26 (default), 24, 22. |

Streaming works from an ordinary Next.js route handler on the default Node.js runtime; it does not need the edge runtime ([Vercel: streaming functions](https://vercel.com/docs/functions/streaming-functions), [Next.js on Vercel](https://vercel.com/docs/frameworks/full-stack/nextjs)).

One consequence of the 4.5 MB limit: a large source file cannot be sent through a Vercel Function. It has to be read from storage or loaded by a job.

### 2.4 Jobs that outlive a normal web request

| Job | How long | Where it should run | Why |
| --- | --- | --- | --- |
| **Loading the material**: cut up, label, index | Minutes to hours for the whole Course | Depends on ticket #4. If search runs inside OpenAI, loading is mostly uploading files and may fit in one request. If the index lives in Neon, use a **Vercel Workflow**: one step per file, each step retried by itself. | Workflows are generally available, have no limit on total run time, and each step gets the normal function limit. Keys stay in Vercel. |
| **A slow Chatbot answer** | Seconds to minutes | A **streaming Vercel Function**, with its time limit set on purpose | Fits the 300 s default. Can be raised to 800 s. |
| **An answer that might pass the limit, or must survive a closed tab** | Many minutes | **OpenAI background mode**: the job runs at OpenAI and the app follows it or picks the stream back up | No new vendor. Decide after ticket #3 measures real answer times. |
| **Generating a Widget** | Same as an answer | Same streaming function | Same limits. |
| **Work after the answer is sent**: save the conversation, count usage | Under a second | `after()` in Next.js | It runs after the response and shares the function's time limit. It is not retried, so a write that must not be lost belongs before the response ends. |
| **Timed jobs**, if any: resetting caps, clean-up | Seconds | Vercel Schedules, or the older Cron Jobs | Probably none needed in v1. A cap can be worked out by a query. |
| **Changing the database tables** | Seconds | At deploy time, before the new version goes live. Never inside a request. | Where exactly is for ticket #5. |
| **Checking the Chatbot** over a batch of questions | Minutes | A GitHub Actions job started by hand, or a Workflow | "Checking the Chatbot" is not yet specified on the map. |
| **Checking the calculator** against the spreadsheet | Seconds | Ordinary unit tests in CI | Not a long job. |

Sources: [Vercel: background workers](https://vercel.com/docs/background-workers) lists which product fits which job. [Workflows](https://vercel.com/docs/workflows) and [pricing and limits](https://vercel.com/docs/workflows/pricing): no maximum run duration, 10,000 steps a run, $0.02 per 1,000 events on demand. Workflows became generally available on [2026-04-16](https://vercel.com/blog/a-new-programming-model-for-durable-execution). [Schedules](https://vercel.com/docs/schedules) are in beta and replace Cron Jobs, which still work; on Pro, cron jobs can run once a minute ([cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing)). `after()` and its limit: [Vercel functions package](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package). OpenAI background mode: [guide](https://developers.openai.com/api/docs/guides/background).

Not needed: Vercel Queues (public beta, per Vercel's plugin notes) and Vercel Daemons (beta, always-on workers). Nothing in one Lesson calls for them.

### 2.5 What makes a fixed Lesson page feel instant, and what would slow it

**What makes it fast**

| Mechanism | Source |
| --- | --- |
| The page's fixed part is built ahead of time and served from Vercel's network. The personal parts stream into holes left for them, in the same response. | [Vercel: Next.js on Vercel](https://vercel.com/docs/frameworks/full-stack/nextjs) |
| The browser fetches one reusable shell per route as soon as a link is visible. A link can be told to fetch its cached content too, so the next Lesson step is already there on click. | [Instant Navigations](https://nextjs.org/blog/next-16-3-instant-navigations), [prefetching](https://nextjs.org/docs/app/guides/prefetching) |
| A slow navigation is an error during development, and a Playwright helper named `instant()` catches a later regression. | [Instant Navigations](https://nextjs.org/blog/next-16-3-instant-navigations) |
| `ensureStatic` on the Lesson routes fails the build if something on-demand sneaks in. | [Next.js 16.4](https://nextjs.org/blog/next-16-4) |
| Next.js trims imports from `recharts` automatically. | [optimizePackageImports](https://nextjs.org/docs/app/api-reference/config/next-config-js/optimizePackageImports) |

Opinion: put the calculator in plain TypeScript that runs in the browser, so a slider never waits on the network. Keep the Chatbot panel in the layout so it does not reload between steps.

**What would slow it**

| Risk | Source |
| --- | --- |
| Reading who the Student is at the top of a Lesson page. With Cache Components this is a build error unless the personal part is set apart behind a loading boundary. | [Authentication with Cache Components](https://nextjs.org/docs/app/guides/authentication-with-cache-components) |
| Looking up the database in `proxy.ts`. It runs on every route and every prefetch, so it should only read the sign-in cookie. | [Next.js: authentication](https://nextjs.org/docs/app/guides/authentication) |
| Opening a new database connection on each request. A pooled connection skips about eight network round trips. | [Neon: connecting from Vercel](https://neon.com/docs/guides/vercel-connection-methods) |
| The chart library's size. Recharts adds roughly 97 to 113 kB compressed on top of React. | Measured: [TanStack Charts comparison, baseline 2026-10-14](https://tanstack.com/charts/latest/docs/comparison) |
| The model's own thinking time. | Ticket #3 |
| The database being asleep, or in a different region from the function. | Ticket #5 |

**One consequence for sign-in.** A pre-built Lesson page is the same file for everyone, so the invite check has to happen *before* the file is served. Next.js names `proxy.ts` as the place "to protect static routes that share data between users (e.g. content behind a paywall)" ([authentication guide](https://nextjs.org/docs/app/guides/authentication)), and Vercel confirms it "runs before the cache" ([Next.js on Vercel](https://vercel.com/docs/frameworks/full-stack/nextjs)). Ticket #5 should confirm its sign-in choice can do a cookie-only check there.

### 2.6 Reading and writing the database

| Claim | Source |
| --- | --- |
| On Vercel's Fluid compute, Neon recommends "a standard Postgres TCP connection" with a connection pool, and shows Drizzle over `pg` with `attachDatabasePool`. Opinion: Drizzle over Prisma or raw SQL because the schema is plain TypeScript with no extra generate step, it reads like SQL, the earlier attempt already proved it, and it is what Neon's own example uses. Weekly downloads are a weak sign of how much an agent has seen: drizzle-orm 46.7 million, kysely 30.8 million, prisma 24.7 million (npm, week to 2026-11-27).

### 2.10 What "easy for AI coding agents" rests on

| Finding | Source and limits |
| --- | --- |
| A short pointer in `AGENTS.md` to version-matched docs took agents from 53% to 100% on Next.js 16 tasks. Packaging the same docs as an on-demand skill reached 79% at best, and the skill was never called in 56% of cases. | Measured by the vendor: [Vercel, 2026-01-27](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals) |
| By late 2026 the strongest models pass those tasks without the pointer. Cheaper models still gain. | [Next.js agent evals, 2026-10-30](https://nextjs.org/evals) |
| Across real repositories, context files did not generally raise success and added over 20% to cost. Instructions were followed; repository overviews did not help. They are "useful for specifying non-standard coding practices". | Measured independently: [ETH Zurich, arXiv 2602.11988, v3 2026-09-29](https://arxiv.org/abs/2602.11988) |
| A smaller controlled study found no measurable effect of context files on correctness. | [REALM 2026 workshop paper](https://aclanthology.org/2026.realm-1.5.pdf). 17 tasks; it could only have detected a large effect. |
| OpenAI's team keeps `AGENTS.md` near 100 lines as a table of contents and enforces rules with linters and CI, not prose. | First-party practice report: [OpenAI, 2026-02-11](https://openai.com/index/harness-engineering) |
| "Keep it small", and pair it with linters and type checkers. | [OpenAI Codex: customization](https://developers.openai.com/codex/concepts/customization) |
| Keep the context file short and give the agent "something it can run that comes back pass or fail". | [Anthropic: Claude Code best practices](https://code.claude.com/docs/en/best-practices) |
| Typed languages did not help agents finish more tasks. TypeScript did not beat JavaScript once tasks were compared fairly. Agents ran the type checker in 1 of 10 TypeScript runs. The advice: pick by how much code an agent reads, how fast tests run, and how much comes ready-made. | Measured independently: [Evil Martians, 2026-11-24](https://evilmartians.com/chronicles/type-errors-cost-our-coding-agents-under-one-percent-of-their-time) |
| A type checker helped only where the code was already well typed: success rose from about 80% to 84%, with fewer steps. | Measured: [Meta's Pyrefly team, 2026-06-09](https://pyrefly.org/blog/type-checking-agentic-workflows). Python, their own agent. |
| Vercel and Next.js ship first-party agent tooling: bundled docs, a dev-server MCP endpoint, workflow skills, a Vercel plugin, and `vercel agent init`. | [Next.js AI agents guide](https://nextjs.org/docs/app/guides/ai-agents), [Vercel agent resources](https://vercel.com/docs/agent-resources) |

What this adds up to:

- **Supported:** a short `AGENTS.md`; version-matched docs inside the repo's dependencies; one pass-or-fail command; rules enforced by tools; little code and fast tests.
- **Not supported:** "types make agents better". TypeScript is chosen here because it is the one language of this stack and Drizzle needs it. The evidence says keep it strict and ban `any`, or the one measured benefit disappears.
- **Weak:** popularity as a stand-in for what a model has seen.

**Repo habits that follow**

1. Keep `AGENTS.md` under about 100 lines: the commands, the non-obvious rules, pointers to deeper docs. Leave the block Next.js manages untouched.
2. Write down the choices an agent would otherwise get wrong. The main one: use OpenAI's own SDK. Vercel's docs and its [agent plugin](https://vercel.com/docs/agent-resources/vercel-plugin) steer agents toward Vercel's AI SDK and AI Gateway by default, which the map has ruled out. This is exactly the "non-standard practice" a context file is good for.
3. One command, `pnpm check`, runs types, Biome and unit tests.
4. Enforce with tools: no `any`; database code importable only on the server; `ensureStatic` on Lesson routes; the `instant()` check in Playwright.
5. One schema file. Migrations are generated, never hand-written.
6. Stay on the framework's defaults unless this file says otherwise.
7. Add a rule only after an agent makes the same mistake twice.

Items 1, 3, 4 and 7 come straight from the sources above. Items 2, 5 and 6 are opinion built on them.

## 3. Open questions

1. **Does the whole toolchain run together on TypeScript 7?** Next.js, Drizzle's tool, Vitest, Playwright and the shadcn CLI were not installed and run for this research. A ten-minute scaffold answers it. Fallback: TypeScript 6.
2. **Drizzle 0.45 or the 1.0 release candidate?** Starting on 0.45 means one upgrade later. Whichever is chosen, `AGENTS.md` should name it, because Drizzle's docs now show both styles.
3. **Where loading the material runs** depends on the search approach in ticket #4.
4. **Do answers at the reasoning level the owner wants fit inside 300 s, or 800 s?** Ticket #3 and its prototype decide whether OpenAI's background mode is needed.
5. **Can the sign-in choice do a cookie-only check in `proxy.ts`,** and is a pre-built Lesson page really unreachable without an invite? Worth a small prototype in ticket #5.
6. **Where do migrations run,** and against which copy of the database for previews? Ticket #5.
7. **Where does a Lesson's text live?** In the repo it is pre-built at deploy time. In the database it is cached and refreshed. Both can be instant; they differ in how a Lesson is edited. This is the map's "Writing and storing a Lesson".
8. **Can A2UI's React renderer use the shadcn components as its catalog,** so both kinds of Widget share building blocks? Ticket #2.
9. **Does Recharts cover every Widget in the Lesson spec?** A waterfall chart needs a workaround, and a chart of thousands of points would need another library.
10. **Can the spreadsheet logic be rebuilt in TypeScript and match the original numbers?** This is the main thing that could reopen the "no separate backend" answer.
11. **How do Playwright runs in a public repo reach a protected preview,** and which secrets does GitHub need to hold?
12. **React Compiler on or off?** Off is the Next.js default. Turn it on only if Widget interactions measure slow.

## 4. What could not be confirmed

- That Vercel Services and Vercel Queues are in beta. This comes from the notes inside Vercel's own agent plugin (2026-10-29), not from a public docs page read in full.
- The security fixes in 16.4.1 were read from a quoted copy of the release notes, not from the advisory pages.
- Download counts show how widely a tool is used. They do not show how well an agent handles it. No source measured Drizzle against Prisma, Biome against ESLint, pnpm against npm, or Recharts against its rivals *with agents*.

- Weights of chart libraries differ by how they are measured: 97 to 172 kB for Recharts across the two builds cited.
